# Remembrance Capsule · product preview

[Open the capsule preview](https://aruintelligence.github.io/aru-remembrance-field/capsule/). This is a separate, local-only gift experience alongside the Remembrance Field research simulation. It is a functional prototype, not an AI chat service or a finished commerce product.

## Make and open a gift

1. Enter the recipient's name, your name, a letter, and one to eight memories. Add optional PNG, JPEG, or WebP photos of up to 600 KB each. For voice, press **Record a voice note** to request microphone access, record for up to 30 seconds, stop, and listen before adding the memory. Or choose an M4A, MP3, WAV, or WebM file of up to 1 MB per memory. The recorder selects an available MP4/AAC or WebM format and offers the file chooser if recording is unavailable; recording and playback support vary by browser. On an iPhone, [Voice Memos can also export a recording to Files as M4A](https://support.apple.com/en-asia/guide/iphone/iph831c37815/ios); trim it if it exceeds the limit. **Save private draft** downloads an encrypted checkpoint at any point, including an unfinished letter or the memory, selected photo, or selected audio currently in the editor. **Resume draft** restores it later with its private passphrase; it asks before replacing work already on the page. Optional **Enable encrypted recovery** saves encrypted snapshots on this browser after edits. It starts only when you enter and confirm a private recovery passphrase. **Restore on-device copy** needs that passphrase again after a reload; **Forget recovery copy** removes it. Stop recording before a checkpoint; recovery waits for recording to stop. Download private draft files as a separate backup, and use a different passphrase for the finished gift.
2. Preview the gift. Choose a unique passphrase of at least 12 characters and select **Seal and download** or **Seal for sharing**. Both create a versioned JSON file encrypted with AES-256-GCM and a key derived with PBKDF2-SHA256 (310,000 iterations, random 16-byte salt, random 12-byte IV). On a device that supports file sharing, tap **Share sealed file** after sealing and choose the destination in the device's share sheet. Sharing is a separate tap because browsers require user activation when opening that sheet. If sharing is unavailable, use **Download prepared file** and share it from Files. The share sheet receives the encrypted file only, never the passphrase. A closed share sheet is not proof that the recipient received the file.
3. Give the recipient the file and tell them the passphrase **separately**, after confirming they have the file. They choose **Open a gift**, select the file, and enter the passphrase. They can read, listen, copy written stories, and ask questions about the written memories. Audio playback depends on the recipient's browser and supported codecs. The question feature searches written words only; it does not transcribe recordings. It returns matching source cards with attached voice notes or refuses to invent an answer. It is deterministic word matching, not a language model. **Edit a copy** loads an opened gift into the maker form; it never overwrites the original file and requires a new sealed file to preserve changes. While online, the recipient can tap **Save reader for offline use** on this tab and bookmark the page. After the success message, the page and its code can load from this browser's cache without a connection; they still need the sealed file and passphrase. Offline storage depends on browser support and may be cleared by the browser or user.

The fictional sample is available without a file or passphrase. It has written stories only; no real person's story, photo, or voice is bundled. To run a local checkout, serve the repository over localhost (for example, `python3 -m http.server 8000`) and open `http://localhost:8000/capsule/`; browser module loading and Web Crypto may not work from `file://`.

The maker includes optional story prompts. They are writing guidance only and never inserted into the sealed gift. After opening, the reader offers up to three starter questions drawn from the actual written memories. Each suggestion is checked against the same local word matching used for typed questions, so selecting it leads to an authored source memory. These prompts do not generate or verify facts.

The maker can move saved memories up or down to set their presentation order. A move invalidates a previously prepared sealed file and is included in the next private draft or recovery snapshot. Save or cancel a current memory edit before reordering. In the reader, **Read one at a time** presents the letter's memories as a sequence with previous and next controls; **Show all memories** restores the full view. Changing views or memories pauses voice playback. This reading position stays in the current page session only.

After opening a capsule, **Print or save PDF** opens the browser's print dialog. The print layout contains the letter, written memories, and their photos in the maker's order, even when the reader is displaying one memory at a time. It does not print the opening form, question results, passphrase, or audio controls. Voice notes remain in the encrypted digital gift. A paper copy or saved PDF is readable without a passphrase; keep it private and choose the printer or PDF destination deliberately. The app does not create, upload, or store a PDF itself.

After sealing, **Copy opening steps** copies a short handoff note with the reader's canonical page link and file-opening instructions. It includes a 16-character file match code derived from the encrypted file, but no story, name, file bytes, or passphrase. The recipient sees the code immediately after selecting the encrypted file, before entering a passphrase, and can compare it to the opening steps to catch a file mix-up. The code also appears after opening. A matching code alone does not validate or open the file. The code is not an author identity check: anyone who can replace both the file and message can supply a matching code. Copying does not send anything; choose your own destination after confirming that the recipient has the encrypted file, and give the passphrase separately. Editing the gift invalidates the prepared file and disables this handoff until it is sealed again.

## Boundaries

- The app makes no automatic content uploads. By default it does not store a draft, passphrase, or opened gift in browser storage. If you opt in to recovery, it stores one encrypted private draft in IndexedDB on this origin. It clears the passphrase fields after activation and keeps a nonextractable Web Crypto key in memory only for the current page session; the key and passphrase are not saved in IndexedDB. Edits save after a short pause and a completed storage transaction, not instantaneously. Leaving or refreshing pauses recovery; you must enable it again for new edits. A second tab that takes over the stored copy stops the older tab from overwriting it. The optional offline reader separately stores only an exact, versioned copy of this page and its two JavaScript modules in Cache Storage. Installation verifies the SHA-256 digest of all three files before activating, and the worker responds only to requests for those exact reader assets. It does not cache a selected file, draft, passphrase, or unrelated site request. A first visit and offline setup require a connection; browser storage eviction or changes to this site's future code can affect availability. If you tap **Share sealed file** and choose a destination, that destination receives the encrypted file; this site does not choose the recipient. The passphrase is never placed in the share payload. Microphone access is requested only after pressing **Record a voice note**, and its stream is stopped when recording ends or the page is left. Local recovery is not an external backup: save private draft files after important changes and keep copies deliberately. Changes made just before a crash may not have reached storage. Lost passphrases cannot be recovered here.
- A private checkpoint and an on-device recovery copy use a distinct versioned format and authenticated encryption with the same PBKDF2-SHA256 / AES-256-GCM parameters as a finished gift. Recovery derives a fresh salt and IV for each snapshot. It cannot be opened as a recipient gift, and a finished gift cannot be resumed as a private checkpoint. Only give the recipient the finished file, not your private draft.
- The sealed file contains encrypted stories, photos, and voice notes. Anyone with both file and passphrase can decrypt, copy, and reshare them. A guessable passphrase is susceptible to offline guessing; PBKDF2 does not turn a weak passphrase into a strong one. This prototype has not had an external security audit.
- Encryption detects changes to the sealed bytes when opened with the correct passphrase. It does not identify the author, prove a story true, prevent the maker from changing stories before export, or guarantee confidentiality on a compromised device.
- The recipient must trust the page serving this code. The GitHub Pages site is an ordinary web origin whose future code could change. A locally reviewed checkout can be served without internet. The file itself is portable because the source and documented format are in this repository.
- Memories are limited to eight, individual stories to 2,400 characters, photos to 600 KB, audio to 1 MB per memory, and a sealed file to 27 MB. New version 3 gift and draft files support WebM as well as M4A, MP3, and WAV; the reader still opens version 1 and 2 files. Saving an older gift or draft again upgrades its format without discarding its voice note. File headers are checked, but that alone cannot guarantee a recording will decode or that its contents match its description. No accounts, collaboration, payment, live AI model, or cross-device sync are implemented.

## Reproducible checks

```bash
node --test tests/capsule*.test.mjs
```

The tests cover encrypt/decrypt, fresh salts and IVs, wrong passphrases, changed ciphertext, unsupported parameters, bounded imports, rejected SVG/spoofed images, cited lexical recall, unfinished checkpoints, real decodable M4A/MP3/WAV/WebM fixtures, version 1 and 2 encrypted file migration, separation between gift and draft formats, a mocked share flow that rejects stale gifts and excludes plaintext from the file, a service worker harness that checks offline shell integrity, request isolation, and failed install rollback, and a recovery flow that exercises opt-in, encrypted changes, restore, wrong passphrases, and a second-tab conflict. A passing local test does not establish commercial readiness or independent security validation. Actual iPhone storage behavior, offline use, microphone permissions, playback, and the device share sheet need device checks.

After changing `core.mjs`, `app.mjs`, `index.html`, or `offline-worker.js`, run `node tools/update-capsule-assets.mjs` before committing. The content hashes in the module URLs keep a newly deployed page from loading older cached JavaScript. The script also updates the offline worker's exact asset digests and cache version, including changes to worker logic. The capsule tests fail if those values do not match the current files.
