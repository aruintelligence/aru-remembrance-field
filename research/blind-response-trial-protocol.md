# Blind response trial protocol

## Question

For this scripted response layer, do readers prefer the response that used earlier context over the response generated without earlier memory? Preference is a human judgment about usefulness for a specific prompt. It is separate from the app's modeled μ score.

## One trial

1. Write 1–8 context lines (up to 500 characters per line) and one final prompt (up to 500 characters). Keep them non-sensitive if the result will be shared.
2. Open **Blind response trial** in the inspector and run the pair. The app starts both branches at μ = 0.6400 with a fixed clock. Both receive the same context in order. The control carries its score forward but discards prior memory and messages before every step. Only the other branch carries prior history.
3. Select **Begin reader rating** and ask a reader who did not write the context to choose A, B, or tie/neither in the focused reader view. It shows the context and final prompt but blocks the surrounding inspector and its modeled scores. Closing without rating preserves the same randomized pair for **Reopen reader view**; changing the input clears it. Do not reveal the branch assignments or modeled scores until the choice is submitted. The response content itself may give clues about the branch, so this hides labels rather than guaranteeing complete blinding.
4. Reveal the assignment and download the JSON if the trial may be audited. Nothing is saved automatically. The report contains the full entered text and the rating.
5. Run `node tools/verify-blind-trial.cjs /path/to/aru-blind-response-trial.json` from a local checkout to recompute both score receipts and response strings. A changed context, score, or response fails. The verifier cannot authenticate the rating, randomization, person, or original file.

Current exports declare `model_revision: "aru-field-heuristics-3"` and `response_revision: "aru-response-2"`. The renderer withholds an earlier memory from the response if it detects a direct `not <word>` polarity mismatch or one of the score model's literal contradiction pairs. V3 skips overlap from a directly mismatched memory entry and applies a `−0.03` direct negation term when a last-ten entry mismatches. The saved memory stays intact. This lexical check can miss an implicit correction, and shared words can trigger a false warning. The older score and response renderers are archived, so earlier reports remain replayable. Keep both revisions fixed throughout a study.

For a set of exported reports, run `node tools/analyze-blind-trials.cjs /path/to/trials/*.json` (or add `--json` before the paths for a machine-readable summary). Supply every completed trial. The analyzer checks each report with that verifier before counting it and stops without a partial scorecard if one fails. It reports history wins over all reports, control wins, ties, the history fraction among non-ties, and outcomes split by whether history appeared in A or B. A zero non-tie denominator is explicitly undefined. Byte-identical reports are counted and flagged, because separate ratings can produce identical files; deduplicating them automatically would erase possible participants. The dataset SHA-256 fingerprints the multiset of supplied file bytes, independent of file order. It is not a signature or proof of collection. Each file is limited to 1 MiB; the tool accepts up to 100 files and 16 MiB in total.

The [score versus preference audit](score-preference-audit.md) adds a three-by-three comparison of modeled score direction with the recorded choice, including choices against the higher score. It also shows a Wilson 95% interval for the primary all-ratings history preference fraction, conditional on independent ratings. When using a fixed plan, the output identifies score direction and decisive agreement/opposition for each case ID. These are diagnostics on the supplied files, not evidence that an interval's sampling assumptions or any rating's origin can be verified.

### Fixed trial plan

Before inviting readers, write and publish a plan JSON with `format: "aru-blind-trial-plan"`, `version: 3`, `model_revision: "aru-field-heuristics-3"`, `response_revision: "aru-response-2"`, `primary_outcome: "history_win_fraction_all"`, and a `cases` array. Each case has a unique short `id`, the exact `context` lines, one exact `prompt`, and `ratings` (the number of completed ratings expected). Keep context/prompt pairs unique. Up to 50 cases and 100 total ratings are supported. Run `node tools/analyze-blind-trials.cjs --check-plan /path/to/plan.json` to validate it and print its SHA-256. Publish the plan and this hash before collection so others can compare the later analysis to the same file; do not revise it after seeing outcomes. In the browser trial, choose **Optional fixed trial plan JSON**, select a case, ask the reader to rate A/B/tie, and download that rating before moving to another case. Repeat for every expected rating. Planned downloads include the case ID and a timestamp in the filename so consecutive ratings do not all receive one name. A changed input clears the case selection; the plan stays in page memory only. Keep one exported trial file per completed rating. The CLI still accepts older version 1 and 2 plans and their matching reports; the current browser loads only version 3 plans. The analyzer rejects reports with a different score or response revision from the plan, and mixed revisions even without a plan.

Run `node tools/analyze-blind-trials.cjs --plan /path/to/plan.json /path/to/trials/*.json`, or add `--json` before `--plan` for a machine-readable result. The tool replays every report, rejects an unplanned prompt or too many ratings for a case, and refuses to print a scorecard while any planned case is short. The result records the plan's byte-level SHA-256 and coverage by case ID without echoing any prompt text. Try the [current synthetic plan](example-blind-trial-plan-v3.json) with `node tools/analyze-blind-trials.cjs --plan research/example-blind-trial-plan-v3.json research/example-blind-trial-v3.json`; it deliberately reports one tie. The [v1 plan](example-blind-trial-plan.json) and [v2 plan](example-blind-trial-plan-v2.json) are retained as compatibility checks. A matching plan checks the files you supply against expected counts; it cannot prove that no completed files were withheld, that the plan was really published in advance, or that ratings came from independent people.

## A credible pilot

Before collecting ratings, publish a fixed set of prompts, a rule for choosing context, a target number of independent readers, and the primary outcome: the fraction choosing the history response among **all** rated trials, with ties shown separately. Keep every completed trial, including control wins and ties. Avoid selecting examples based on their μ difference or after seeing a reader's choice. A person should not rate the same prompt twice, and authors should not rate their own prompts. Report the raw counts for history wins, control wins, and ties, with the denominator and prompt set; include uncertainty intervals if making a broader claim. Inspect whether an apparent advantage survives prompts where history is unrelated or misleading.

The app only provides one local trial at a time. The reader view reduces accidental exposure to modeled scores but cannot establish that the person did not see the plan or infer the condition from the wording. The batch tool calculates descriptive counts for supplied files; neither component collects participants, enforces the pilot procedures, estimates a population effect, or authenticates JSON. Even different file hashes do not establish distinct readers, and reported positions do not prove randomization. An independently run study would need consent and a separately managed data collection process. The included synthetic examples and software tests do not measure a human preference or establish a commercial benefit.
